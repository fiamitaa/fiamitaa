代理订阅链接泄露了怎么办？

删掉消息之后，怎样重置链接、撤销旧凭据并安全求助？

如果订阅链接或二维码被发进公开群组，先把它当作凭据。撤下公开内容以后，还要确认旧链接和已经导出的节点配置是否有效。

如果内容已经被复制、下载或截图，撤回消息无法收回这些副本。需要继续处理的是链接背后的访问权限。

订阅链接可能带着什么

很多订阅地址包含访问令牌。拿到完整地址的人，可能不需要登录你的账户，就能下载对应的节点配置。具体能做什么，取决于服务商的认证方式和权限设计。

以 Mihomo 的 HTTP 代理集合为例，它可以通过 URL 下载配置，也支持认证请求头；节点配置又可能包含连接所需的密码等字段。[1][2] 因此，订阅地址、下载后的配置和节点二维码，都应检查是否包含凭据。

能下载订阅，不一定就能修改账户或查看支付信息；反过来，即使没有账户管理权限，也可能已经足够使用连接服务。不要因为链接里没有明文密码，就认为可以公开。

HTTPS 保护传输，不能替你保管截图

HTTPS 可以保护正常证书校验下的传输，但完整 URL 仍可能出现在浏览器历史、应用日志、服务端日志或别人保存的截图里。

OWASP 专门介绍了 URL 查询参数中敏感信息的泄露问题：令牌放在地址里，即使使用 HTTPS，也不能消除历史记录和日志等位置的暴露风险。[3] 某些跳转和页面行为还可能涉及来源信息，是否传递完整地址取决于浏览器策略和具体实现。

二维码也没有额外的保密作用。它只是把内容变成了便于扫描的形式，遮住旁边的文字却保留二维码，仍可能把完整信息交出去。

发现泄露后，按权限处理

先停止继续传播，删除能控制的公开副本，再通过服务商提供的功能撤销或重置权限。不要为了让更多人判断风险，把原链接转发到另一个群里。

可以按下面的顺序操作：

  1. 删除或编辑公开消息、截图和仓库文件，通知管理员协助清理仍可访问的内容。
  2. 从自己核实过的官网或客户端进入账户，找到重置订阅、撤销令牌或相关安全功能。
  3. 按服务商说明更新自己的客户端，并核对旧链接是否还可下载。
  4. 确认已下发的节点凭据是否也会失效；说明不清楚时联系官方支持。
  5. 查看账户状态与流量记录，保留异常时间和必要证据。

重置可能影响自己其他设备上的连接。处理后记得逐台更新，不要把这些设备的失效误认为新的服务故障。

如果没有重置入口，也不要只等着观察流量。向支持人员明确说明“连接凭据可能已经泄露”，询问可撤销的范围和处理方式。

新订阅地址生成了，旧节点未必马上失效

订阅下载和节点连接可能使用不同凭据。重置下载地址，可以阻止旧地址继续获取配置；已经下载的配置还能不能连接，则要看节点凭据是否轮换、服务端是否撤销旧权限。

这两件事不能混为一谈。

联系支持时可以这样问：

我已经重置订阅地址。旧地址是否立即失效？此前下载的节点配置还能连接吗？是否还需要轮换节点凭据，或执行其他撤销操作？

验证也要分开看。旧链接无法下载，只证明这条下载路径失效，不足以证明旧配置的连接权限已撤销。需要测试时，仅使用自己的账户和配置，按服务商给出的方式核对，避免把秘密交给第三方“检测网站”。

链接进过公开仓库，要先撤销凭据

只在最新文件中删掉链接，旧提交里可能仍然留着；公开内容也可能已经被克隆或缓存。

因此，先让泄露的凭据失效，再处理仓库历史和其他副本。清理历史有助于减少继续暴露，但不能保证收回已经被复制的内容。代码托管平台的具体处理方式另查其文档，不要把“网页上搜不到了”当作撤销证明。

如果同时暴露了账户密码或 API 密钥，也要分别修改或撤销。订阅令牌、账户密码和支付信息的权限不同，不能指望重置一个项目就覆盖全部风险。

求助时，留下错误，把秘密删掉

排查通常需要的是客户端版本、系统、发生时间、错误原文和复现步骤。完整订阅地址、二维码、密码、UUID、私钥和认证请求头，往往没有必要公开。

发截图前，可以检查三个位置：订阅管理页的地址栏，节点详情中的认证字段，以及日志中的请求 URL。用不透明色块遮住内容后导出图片，再重新打开检查。不要只在图片上加一层半透明高亮。

分享文字配置时，把相关值换成明确占位符，例如 YOUR_TOKEN、YOUR_PASSWORD。地址可以使用 example.com，同时保留定位问题需要的字段名和结构。

如果没有把握判断哪些内容是凭据，先发错误文字和环境信息，让支持人员指出还缺什么。确认官方私密渠道后，再提供处理账户所必需的最少信息。

没看到异常流量，也要完成撤销

流量统计可能延迟，泄露内容也可能暂时没有被使用。账户暂时正常，不能证明链接从未被复制。

处理这类问题，更可靠的结束条件是：服务商确认相关旧权限已撤销，自己的设备已更新，公开内容也已尽可能清理。以后求助时保留同一份脱敏模板，就能少一次临时翻找和误发。
