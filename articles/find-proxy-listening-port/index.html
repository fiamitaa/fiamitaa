代理端口是谁在监听？Windows、macOS 和 Ubuntu 查询方法

查询监听地址、端口和对应进程，区分客户端未启动与端口占用。

客户端填的是 7890，curl 却提示连接被拒绝，先查这个端口有没有程序监听，再看是谁在监听。这样才能分清客户端没启动、端口填错，还是被其他程序占用。

本文以 TCP 端口 7890 为例。它不是固定默认值，请先在客户端设置中确认实际 HTTP、SOCKS5 或 Mixed 端口，再替换命令里的数字。下面都是查询操作，不会终止进程或修改防火墙。

Windows：查端口，再查进程

在 Windows 11 开始菜单搜索“终端”，打开 PowerShell，执行：

Get-NetTCPConnection -State Listen -LocalPort 7890 | Select-Object LocalAddress, LocalPort, OwningProcess

LocalAddress 是监听地址，LocalPort 是端口，OwningProcess 是进程 ID。[1] 假设结果里的进程 ID 是 1234，继续查询：

Get-Process -Id 1234 | Select-Object Id, ProcessName, Path

1234 只是示例，要换成刚才查到的 ID。不要把 ID 赋给 $PID，那是 PowerShell 自带变量。

如果没有匹配结果，PowerShell 可能显示“未找到对象”；通常表示查询时没有匹配的 TCP 监听项。先检查端口、客户端核心状态，并再次查询。若报权限错误，使用“以管理员身份运行”重新打开终端；某些进程路径也只有提升权限后才能读取。

查到的是客户端内置核心而不是界面程序，也可能正常。将进程名称、路径和客户端的核心信息一起核对，别只看一个陌生名字就结束任务。[2]

macOS：用 lsof 查监听

按 Command + 空格打开“终端”，执行：

lsof -nP -iTCP:7890 -sTCP:LISTEN

-n 不将地址反查为主机名，-P 保留数字端口，最后一个选项只显示 TCP 监听。查看输出中的 COMMAND、PID 和 NAME：分别对应程序名、进程 ID 和监听地址。[3]

没有输出时，先确认端口和客户端状态；需要查看其他用户或系统服务时，再执行：

sudo lsof -nP -iTCP:7890 -sTCP:LISTEN

输入密码时终端不显示字符，属于正常行为。查到 PID 后，例如 1234，用下面的命令查看更完整的启动命令：

ps -p 1234 -o pid=,comm=,args=

如果 lsof 不存在，先用 command -v lsof 检查命令路径，并核对系统工具安装情况。分享 args 输出前，留意其中可能包含的配置路径或凭据。

Ubuntu：用 ss 查监听

Ubuntu 桌面版按 Ctrl + Alt + T，服务器版使用当前 shell，执行：

ss -ltnp 'sport = :7890'

-l 只看监听，-t 只看 TCP，-n 保留数字地址和端口，-p 显示可见的进程信息。过滤条件限定本地端口，避免把远端连接误看成监听。[4]

重点看 Local Address:Port 和 Process。普通用户可能看不到其他用户的进程信息，需要时执行：

sudo ss -ltnp 'sport = :7890'

若提示找不到 ss，它由 iproute2 软件包提供，可安装后重试：

sudo apt update
sudo apt install iproute2

拿到 PID 后，例如 1234，继续查看程序命令：

ps -p 1234 -o pid=,comm=,args=

只有表头、没有记录时，表示没有找到匹配项。检查客户端是否已启动、端口是否修改，以及是否在容器或其他网络命名空间内运行；容器里的监听不一定直接出现在宿主机查询结果中。

监听地址怎么理解

监听地址 含义
127.0.0.1:7890 IPv4 本机回环，供同一网络命名空间内的本机程序连接
[::1]:7890 IPv6 本机回环；不代表 127.0.0.1 也能连接
0.0.0.0:7890 或 *:7890 通配监听；结合输出的地址族确认具体范围
[::]:7890 IPv6 通配监听，是否同时接收 IPv4 取决于系统和套接字设置
某个局域网 IP 绑定到该地址，是否能从其他设备访问还取决于路由、防火墙和认证

只给本机应用用时，通常不需要为了排查而改成所有地址监听。查询发现通配监听，也不等于端口已经能从公网访问，需要结合防火墙和网络拓扑判断。

查到了监听，为什么仍然不能用

监听只证明程序正在等待 TCP 连接，不能证明它提供 HTTP 或 SOCKS5，也不能证明上游节点正常。核对进程后，用 HTTP 代理验证 或 SOCKS5 代理验证继续测试。

如果端口被其他程序占用，先查清用途。可以在代理客户端改一个空闲端口，再同步修改使用它的应用配置；不要直接结束系统进程。若只是查询，本次操作没有需要恢复的网络设置。
