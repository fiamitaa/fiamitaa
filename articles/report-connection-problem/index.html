“昨天还好好的，今天连不上。”客服看到这句话，还需要问几点、哪个节点、哪个应用、报了什么错。提交时把这些信息放在一起，对方才有条件查服务状态或复现你的问题。

描述一次失败，最好再给一个对照

记下发生时间和时区。写清是更新订阅失败、选中节点后请求超时，还是只有某个应用打不开。然后挑一个容易重复的操作，记录你点击了什么、预期看到什么、实际显示了什么。

如果已经做过对照，把结果附上。例如在同一设备和网络下，换一个节点是否恢复。每次只改一个条件，客服就能看出差异来自哪里。例子里写的现象要与自己实际观察一致，猜测可以留到查完日志之后。

脱敏日志片段：

如果问题只在晚上出现，尽量记下一次失败和一次恢复的时间。对偶发故障，这通常比贴一张没有时间的测速截图更便于核对。涉及订单时，通过核实过的客服入口提交对方处理所需的信息。

附件里保留错误和时间

从日志里选取出错前后几行。留着时间、错误码和相关字段名，把完整订阅地址、令牌、二维码、密码、私钥和认证头去掉。发布到公开问题区之前，再打开导出的图片确认遮挡已经生效。

带令牌的 URL 即便通过 HTTPS 传输，也可能留在日志或浏览器历史里。[1] 如果排查需要说明配置结构，可以用脱敏后的片段，保留字段和值的类型。自己的真实订阅链接无需贴进截图。

收到回复后，按对方建议只改一项，重复同一个操作。回报成功或失败、发生时间以及新的错误原文。这样前一轮反馈留下的条件，下一轮还能用来对照。
