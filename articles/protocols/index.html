代理协议详解：从 HTTP、SOCKS5 到 VLESS、WireGuard

从 HTTP、SOCKS5 到 WireGuard，分清通信规则、传输与安全层。

机场订阅里常能看到 Shadowsocks、VMess、VLESS 或 Trojan。换一个节点，协议名称可能也变了，但名字不同，不代表其中一个一定更快、更稳定。真正容易混淆的是：这些名称并不都处在同一层。HTTP、SOCKS5、Shadowsocks、VMess、VLESS、Trojan、WireGuard、OpenVPN 常被放在一张表里，但它们的定位、覆盖范围和使用方式并不一样。

区分名称时，可以对照它负责的工作：

  • 客户端：用户操作的图形界面或命令行程序；
  • 核心：真正执行连接、认证、路由和流量转发的程序；
  • 协议：客户端与服务端之间遵守的通信规则；
  • 传输与安全组件：TCP、UDP、QUIC 参与传输；TLS 负责安全保护；WebSocket、gRPC 等可能被用作承载方式，它们不在同一层；
  • 配置：把地址、端口、密钥、规则和传输参数组合起来的文件。

例如，Clash Verge Rev 是客户端，Mihomo 更接近核心；v2rayN 是客户端，Xray 和 V2Ray 更接近核心；WireGuard 和 OpenVPN 则更多出现在 VPN 隧道生态中。

先把常见名称放回各自的位置

名称 主要用途 看配置时要留意什么
HTTP、SOCKS5 代理请求或连接转发 应用支持范围、认证、代理链路是否受保护
Shadowsocks 加密代理 密码套件与密钥是否匹配
VMess、VLESS、Trojan 代理连接与认证 核心版本、传输方式和安全配置
WireGuard、OpenVPN VPN 隧道 路由范围、密钥或证书、DNS 设置

这张表用来辨认角色，不是性能排名。下面分别看它们能做什么，以及哪些事不能仅凭名称判断。

HTTP 代理

HTTP 代理常用于网页请求：浏览器把请求交给代理，代理再访问目标网站并返回结果。HTTP 的 CONNECT 方法还可以建立到目标的隧道，HTTPS 访问常会用到它。能否承载某类连接，要看代理与应用的支持范围，不能只凭“HTTP”这个名字判断。[3]

HTTP 代理本身不等于加密。是否安全，要看客户端到代理之间是否有保护、目标网站是否使用 HTTPS，以及代理服务商是否可信。

SOCKS5

SOCKS5 更像一个通用连接转发层。RFC 1928 定义了 CONNECT、BIND 和 UDP ASSOCIATE 等命令，但具体客户端或服务端未必把每项能力都实现了。浏览器、下载工具和其他网络应用是否支持，也要分别确认。[4]

但它同样不自动提供匿名或端到端加密。SOCKS5 只是规定了请求如何交给代理服务器，不能单独证明代理运营者不会记录或修改数据。

Shadowsocks

Shadowsocks 通常被归入加密代理工具。客户端和服务端需要匹配的加密参数与密钥材料，再由服务端转发请求；不同版本的密码套件和配置要求可能不同，应以项目文档为准。[5]

加密代理保护的是特定通信链路，服务端仍然需要你信任。除了看协议名称，也要问清楚：配置来自谁，服务端由谁维护？

VMess、VLESS 与 Trojan

VMess、VLESS 常出现在 V2Ray 或 Xray 相关配置中。它们属于代理协议；TLS 等安全组件以及 WebSocket、gRPC 等承载方式，则是另一些配置维度。哪些组合可用，需要看对应核心和版本，不能随意排列组合。

VLESS 是 Xray 生态里常见的协议名称，VMess 则是 Project V 生态中较早出现的协议名称。Trojan 通常基于 TLS 建立代理连接。它们不能简单排成“从弱到强”的排行榜，因为实际结果还取决于服务端、证书、客户端、核心版本、传输方式和配置。

不能把“使用 VLESS”直接当成“已经启用某种加密”的证明。Xray 官方文档会分别说明 VLESS 的加密设置和传输安全要求；旧教程中的字段解释，未必适用于当前版本。新手应核对完整配置与版本说明，不要凭协议名称猜测安全性。[6]

**协议名称也不等于匿名程度。**协议可以规定如何认证和传输，但不会替你处理账号、Cookie、浏览器指纹或服务商日志。

WireGuard

WireGuard 是 VPN 隧道协议和软件项目。官方文档介绍了它基于公钥的身份机制和所用的密码学组件。[1]

它通常用于设备与 VPN 服务端之间建立系统级隧道，适合远程接入、保护网络传输和多应用统一转发。它不等同于 HTTP 代理或 SOCKS5，也不等同于某个商业 VPN 服务。

WireGuard 协议本身可以设计得很简洁，但服务商是否可靠、密钥如何保存、哪些流量进入隧道，仍然需要单独判断。

OpenVPN 和 IKEv2/IPsec

OpenVPN 是成熟的开源 VPN 项目，常使用 TLS 进行认证和密钥协商。[2] IKEv2/IPsec 则是一组常见于系统和企业网络的 VPN 技术。

它们更偏向系统级隧道，平台支持、证书管理和企业部署经验比较丰富。缺点是配置项较多，新手可能遇到证书、路由、DNS 和权限问题。

WebSocket、gRPC、QUIC 不是同一种协议

这些名称经常跟代理配置一起出现，但不能统称为代理协议：

  • WebSocket：支持客户端和服务器之间建立长连接；
  • gRPC：一种常见的远程调用和通信框架；
  • QUIC：基于 UDP 的现代传输协议；
  • TLS：提供身份认证和加密传输能力的安全协议。

它们可能作为某种代理协议的承载方式。看到配置中出现这些词，不代表连接自动更快、更安全或更匿名。

为什么同一台设备上会同时出现 SOCKS5 和 VLESS

比如，浏览器连接电脑上的本地 SOCKS5 端口，核心再通过 VLESS 连接远程节点。这时 SOCKS5 描述浏览器与本地核心的接口，VLESS 描述核心与远程服务之间的连接，两者并不冲突。

同样，客户端开启 TUN 后可以接收更多应用的流量，但远程节点仍可能使用 Shadowsocks 或 Trojan。TUN 是流量接管方式，不能据此判断远程使用了哪种协议，也不能把它直接等同于 WireGuard。

如何比较协议

不要只问“哪个协议最好”，而要看具体需求：

  • 需要单个浏览器访问，还是整台设备的多应用连接？
  • 更重视速度、低延迟，还是兼容性和维护便利？
  • 服务端由谁提供，日志政策是否透明？
  • 客户端和核心是否仍在维护？
  • 配置是否来自可信来源？

看机场推荐或比较机场节点时，也别把协议名当成线路质量证明。晚高峰负载、路由、丢包和服务端资源都会影响体验；没有具体环境和测量结果，很难只按协议名称判断哪个更稳。

回头看一份配置时，可以沿着这条线理解：协议规定怎么通信，核心负责执行，客户端提供管理界面，配置把它们组合起来。这样再看那些常被并列的名称，就能分清它们各自负责什么。
